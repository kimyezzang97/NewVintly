# 사용자 차단

내가 차단한 회원의 글·댓글이 내 화면에서 보이지 않게 한다.

**아직 구현 전이다.** 이 문서는 착수 전 합의용이며, 구현 후 4장을 "구현된 것"으로 바꾼다.

---

## 1. 왜 하는가

스토어 심사 대응이다. UGC 앱은 문제되는 사용자·콘텐츠를 **신고하고 차단**할 수 있는 인앱 수단을 요구받는다(Google Play UGC 정책, App Store 심사지침 1.2의 "the ability to block abusive users"). 콘텐츠 신고는 `docs/design/report.md`로 완료했고, 차단이 비어 있다.

정책 문구는 바뀌므로 착수 시점에 현재 문구를 확인할 것.

차단은 신고와 성격이 다르다.

| | 신고 | 차단 |
| :--- | :--- | :--- |
| 효과 | 운영자에게 접수 | 신고자 본인 화면에서 즉시 숨김 |
| 관리자 개입 | 필요 | 불필요 |
| 데이터 성격 | 감사 로그 (지우지 않음) | **개인 설정** (탈퇴 시 지운다) |

관리자 검토 기능이 아직 없어 신고가 `PENDING`으로 쌓이기만 하는 상태다. 차단은 그 공백을 이용자 스스로 메우는 수단이라 지금 넣는 값어치가 있다.

**유저 신고(`ReportTargetType.MEMBER`)는 하지 않는다.** 심사에서 반려되면 그때 추가한다. 단일 테이블 설계라 enum 상수 하나 + `switch` 분기 하나로 끝난다.

## 2. 결정사항

| # | 결정 | 선택 | 근거 |
| :-- | :--- | :--- | :--- |
| 1 | 차단 효과 | **표시 차단 (단방향)** | 내가 차단하면 내 화면에서만 사라진다. 상대는 아무것도 알 수 없다. 상호작용 차단은 3장 참고. |
| 2 | 중복 차단 요청 | **멱등 처리 (성공)** | 차단은 설정이라 "이미 그 상태"가 오류일 이유가 없다. 좋아요와 같은 방식이고, 409를 쓰는 신고와는 반대다. |
| 3 | 탈퇴 시 차단 데이터 | **삭제** | 개인 설정이라 남길 이유가 없다. 신고 이력을 보존하는 것과 정반대이므로 헷갈리지 말 것. 차단한 쪽/차단당한 쪽 어느 편이 탈퇴해도 그 행을 지운다. |
| 4 | 관리자 화면 | **없음** | 개인 설정이라 운영이 들여다볼 일이 없다. |
| 5 | 자기 자신 차단 | **차단** (403) | 의미가 없다. |
| 6 | 상호작용 | **차단당한 사람은 댓글을 달 수 없다 (403)** | 표시만 가리면 상대가 계속 내 글에 댓글을 달고 다른 사람에게는 그게 보인다. 괴롭힘이 그대로 이어지고 심사 관점에서도 약하다. 상대가 차단 사실을 짐작할 수 있는 것은 감수한다. |
| 7 | 대댓글 | **부모가 가려지면 대댓글도 전부 가린다** | 자리표시자를 남기는 방식보다 구현과 앱이 모두 단순하다. 대가는 아래 참고. |
| 8 | 게시글 상세 직접 접근 | **막지 않는다** | 목록에서만 가린다. `boardId`로 직접 열면 그대로 보인다. 목록을 먼저 받은 뒤에야 도달하는 드문 경로라 비용 대비 효용이 낮다고 판단했다. |

### 7번(대댓글)의 대가

차단과 **무관한 사람의 대댓글도 함께 사라진다.** 차단한 사람의 최상위 댓글 아래에 달린 다른 회원들의 답글이 전부 안 보인다.

그래서 **화면에 보이는 댓글 수와 실제 개수가 어긋난다.** 앱이 목록 길이로 개수를 표시하면 문제가 없지만, 서버가 내려준 `commentCount`를 그대로 쓰면 "댓글 5개"인데 2개만 보이는 상황이 생긴다. `docs/api/block.md`에 명시하고 앱과 맞출 것.

### 8번(상세)의 대가

목록에서 가린 글을 상세로는 볼 수 있어 차단이 반쪽이 된다. 필요해지면 `BoardQueryDslRepository.findById`에 같은 필터를 얹으면 되므로 나중에 바꿀 수 있다.

## 4. 데이터 모델

```
member_block
  block_id     PK
  blocker_id                -- 차단한 사람 (로그인 회원)
  blocked_id                -- 차단당한 사람
  created_at
  UNIQUE (blocker_id, blocked_id)
```

- 물리 FK와 조회용 인덱스는 두지 않는다 (게시판 계열과 동일 방침).
- `UNIQUE`는 정합성 장치라 인덱스 금지의 예외다. 신고와 같은 근거.
- `updated_at`은 두지 않는다. 차단은 수정되지 않고 생기거나 사라진다.

### 탈퇴 시

`MemberService.withdrawMember`에 **삭제**를 추가한다.

```sql
DELETE FROM member_block WHERE blocker_id = ? OR blocked_id = ?
```

신고(`report`)는 남기고 차단(`member_block`)은 지운다. 성격이 달라서다 — 신고는 제재 근거가 되는 감사 기록이고, 차단은 그 사람의 화면 설정이다. `CLAUDE.md` 탈퇴 절차에 이 대비를 함께 적는다.

## 5. 조회에 미치는 영향

차단 필터를 걸어야 하는 지점은 세 곳이다.

| 위치 | 메서드 |
| :--- | :--- |
| `BoardQueryDslRepository` | `findBoardList` (게시글 목록) |
| `BoardCommentQueryDslRepository` | `findCommentsByBoardId` |
| `VintageCommentQueryDslRepository` | `findCommentsByVintageId` |

`BoardQueryDslRepository.findById`(상세)는 결정 8번에 따라 손대지 않는다.

여기에 댓글 작성 경로 두 곳(`BoardCommentService.create`, `VintageCommentService.create`)에 결정 6번의 검사를 넣는다. **검사 방향에 주의할 것** — 막아야 하는 것은 "내가 차단한 사람"이 아니라 **"나를 차단한 사람의 글에 내가 다는 댓글"** 이다. `blocker_id = 상대`, `blocked_id = 나`로 조회한다.

### 무엇을 검사 대상으로 볼 것인가 (착수 후 확정)

착수 전에는 "글쓴이"라고만 적었는데, **매장에는 글쓴이가 없다.** 매장 댓글은 게시글이 아니라 장소에 달리기 때문이다. 구현하면서 아래로 확정했다.

| 경로 | 검사 대상 |
| :--- | :--- |
| 게시판 최상위 댓글 | 글쓴이 |
| 게시판 대댓글 | 글쓴이 + **부모 댓글 작성자** |
| 매장 최상위 댓글 | 없음 (소유자가 없다) |
| 매장 대댓글 | 부모 댓글 작성자 |

**부모 댓글 작성자 검사는 착수 전 계획에 없었다.** 차단은 단방향 표시라 A가 나를 차단해도 A의 댓글은 내게 그대로 보인다. 이 검사가 없으면 제3자의 글에 달린 A의 댓글에 답글로 계속 접근할 수 있어, 결정 6번이 막으려던 경로가 그대로 열린다.

작성자가 이미 탈퇴했으면 통과시킨다. 회원이 사라졌으면 차단 관계도 함께 삭제돼 있다.

### 함정 1 — `NOT IN`은 NULL을 걸러낸다

탈퇴 회원의 콘텐츠는 작성자가 비어 있다(`vintage_comment.member_id`는 null, `board`/`board_comment`는 orphan 값). 여기에 그냥 `notIn`을 걸면

```sql
member_id NOT IN (5, 9)   -- member_id가 NULL이면 결과가 NULL → 행이 사라진다
```

**차단과 무관한 탈퇴자 글이 통째로 안 보이게 된다.** null을 명시적으로 통과시켜야 한다.

```java
member.memberId.isNull().or(member.memberId.notIn(blockedIds))
```

### 함정 2 — 차단 목록이 비어 있을 때 (착수 전 예상이 빗나갔다)

대부분의 사용자는 차단이 0건이다. **착수 전에는 빈 목록으로 `NOT IN ()`을 만들면 SQL이 깨진다고 적었는데, 실제로는 그렇지 않았다.** 가드를 제거하고 테스트를 돌려도 전부 통과한다 — QueryDSL이 빈 컬렉션의 `notIn`을 안전하게 처리한다.

그래도 가드는 둔다.

```java
if (CollectionUtils.isEmpty(blockedIds)) return null;
```

- 쓸모없는 조건이 SQL에 실리지 않는다.
- "차단이 없으면 필터가 없다"는 의도가 코드에 드러난다.
- QueryDSL이 아닌 경로(JPQL·네이티브 쿼리)로 바뀌면 그때는 실제로 문제가 된다.

즉 **버그를 막는 가드가 아니라 의도를 드러내는 가드다.** 없어도 동작한다는 사실을 알고 두는 것과 모르고 두는 것은 다르므로 여기 적어 둔다.

### 함정 3 — 대댓글은 부모를 봐야 안다

결정 7번 때문에 댓글 조회는 두 가지를 걸러야 한다.

1. 차단한 사람이 쓴 댓글 (최상위·대댓글 모두)
2. **차단한 사람의 최상위 댓글에 달린, 남이 쓴 대댓글**

2번은 작성자만 봐서는 알 수 없다. 부모 댓글의 작성자를 봐야 한다. 서브쿼리로 처리한다.

```
parentId NOT IN (
  SELECT boardCommentId FROM board_comment
   WHERE member_id IN (차단 목록) AND parentId = 0
)
```

여기에도 함정 2가 그대로 적용된다 — 서브쿼리 결과가 비면 조건을 붙이지 않는다.

### 계층

`SecurityUtil`을 리포지토리에서 부르지 않는다. 차단 목록은 서비스에서 조회해 리포지토리에 인자로 넘긴다. `findBoardList(keyword, pageable)`의 시그니처가 바뀌므로 `BoardRepository` 인터페이스와 `BoardFacade`까지 함께 손댄다.

### 성능

조회마다 차단 목록을 한 번 더 읽는다. 차단 건수가 적어 지금은 문제가 아니지만, 목록 쿼리에 `NOT IN`이 붙는 것은 **인덱스 적용 전후 비교 소재로 좋다**(이 프로젝트가 인덱스를 의도적으로 비워둔 이유와 맞물린다). 실제로 느려지기 전에는 최적화하지 않는다.

## 6. API (안)

신고와 같은 모양으로 맞춘다.

```
POST   /api/v1/blocks              차단        body: { "memberId": 5 }
DELETE /api/v1/blocks/{memberId}   차단 해제
GET    /api/v1/blocks              내 차단 목록
```

`/api/v1/members/{memberId}/block` 형태도 읽기는 좋지만, 목록 경로가 `/api/v1/members/blocks`가 되어 `{memberId}`(Long) 매칭과 충돌한다. `/api/v1/blocks`가 안전하다.

| 상황 | code |
| :--- | :--- |
| 차단 성공 / 이미 차단 상태 | 200 |
| 자기 자신 차단 | 403 |
| 없는 회원 차단 | 404 |
| 해제 대상이 차단 상태가 아님 | 200 (멱등) |

내 차단 목록은 `memberId` + 닉네임을 함께 반환한다. 앱이 "차단 관리" 화면을 그리려면 닉네임이 필요하다.

## 7. 작업 순서

`CLAUDE.md`의 TDD 절차를 따른다.

1. `MemberBlock` 엔티티 + 리포지토리 (신고와 같은 3-파일 구조)
2. `MemberBlockService` — 차단/해제/목록, 자기 차단·없는 회원 검사
3. 게시글 목록에 차단 필터 (함정 1·2를 테스트로 먼저 고정)
4. 댓글 조회 2곳에 차단 필터 + 대댓글 서브쿼리 (함정 3)
5. 댓글 작성 2곳에 결정 6번 검사 (방향 주의)
6. 컨트롤러 + Swagger + 예외 매핑
7. 통합 테스트 — 차단 후 목록·댓글에서 사라지는지, **탈퇴자 글은 남아 있는지**, 차단당한 사람의 댓글 작성이 막히는지
8. `db/migration/`에 DDL, `.http/block.http`, `docs/api/block.md`(댓글 수 불일치 명시)
9. `CLAUDE.md` 탈퇴 절차에 `member_block` 삭제 추가 + 통합 테스트
